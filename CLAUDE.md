# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm install                       # onnxruntime-node — only the end-to-end test needs it
npm test                          # all differential tests; these gate the deploy
node --test test/movegen.test.js  # one test file
node --test --test-name-pattern "reproduces OpenSpiel" test/movegen.test.js
quarto preview                    # the site (also `npm run serve`)
quarto render                     # build _site/ once
```

CI (`.github/workflows/pages.yml`) runs `npm test` on Node 22 and only then publishes
`_site` to `gh-pages` on every push to `main`.

## What this repo is

The product site at raccoonbg.com: a Quarto website plus a browser port of the
Raccoon backgammon engine that runs the network client-side. The research
write-ups and the Python/PyTorch engine live in the sibling repo
`../raccoon` (published at research.raccoonbg.com).

**There is no build step and no bundler.** Quarto renders `*.qmd`, copies `app/**`
verbatim (`resources:` in `_quarto.yml`), and `app/loader.html` is injected after
the body of every page via `include-after-body`. `app/` is plain ES modules loaded
by the browser as-is — editing a file under `app/` is the whole deployment story
for that file.

## Layout

```
*.qmd, _quarto.yml, _variables.yml, styles.css   the site
app/engine/    board, movegen, encoder, evaluator, xgid, notation, worker
app/ui/        boardview (SVG), game (turn loop), analysis (panel)
app/models/    exported ONNX network + .meta.json contract
app/vendor/    pinned ONNX Runtime Web build, self-hosted (no CDN)
test/          differential tests against fixtures generated by ../raccoon
```

## Architecture

**Mount point.** `app/main.js` boots into every `.raccoon-app` container on the
page; `data-mode="play"` vs `"analyse"` is the only difference between the two
pages (analyse mode sets `autoplay: false`, so the human plays both sides and the
board turns round). Pages without a container exit at the first line, so static
pages stay static.

**Threading.** `main.js` owns an `EngineClient` that lazily spawns
`app/engine/worker.js` on the first request; the ~47 MB network is fetched only
when the engine is first asked to think, with progress messages going straight to
the status line. The worker is deliberately single-threaded: GitHub Pages cannot
send the COOP/COEP headers WASM threads need.

**Position representation** (`app/engine/board.js`) — read this before touching
anything else. A `Position` is always seen from the player on roll: `my[i]`/`opp[i]`
are both in the *mover's* numbering, the mover travels 23→0. Changing sides costs
an index reversal as well as a label swap (`swapPerspective`); relabelling without
reversing yields a mirrored position that evaluates as noise. Indices match the
Python `BoardView` in `raccoon/env/game_wrapper.py`, because the weights were
trained on tensors built from it.

**Decisions, not turns** (`app/engine/movegen.js`). The unit everywhere is one
OpenSpiel *decision*: a plain roll is up to two half-moves; a double is two
consecutive decisions of two half-moves each, the second flagged `midDoubles`. The
published strength numbers were measured with doubles staged exactly this way.
`legalPlays()` returns positions deduplicated by `boardKey` (for the engine);
`legalSequences()` returns move *orders* (for validating human clicks). OpenSpiel's
1352 action indices are deliberately not ported.

**Move selection** (`app/engine/evaluator.js`) mirrors `child_values()` in
`raccoon/train/lookahead.py`: 0-ply value lookahead, one batched forward pass over
the distinct child positions, no search and no policy head. Three things it must
keep doing — children are encoded from the opponent's side and negated; doubles are
scored *jointly* (each first half by its best continuation, worth +0.033 ppg,
two-thirds of the engine's margin over GNU Backgammon); distinct positions are
evaluated once. The network's `equity` output is equity/3 in [-1,1]; multiply by
`equity_scale` (3.0, see the `.meta.json`) for money points.

**The encoder** (`app/engine/encoder.js`) is a port of `raccoon/env/encoder.py`.
Channel order, normalisation divisors and handcrafted features are copied, not
reinvented — drift here is silent strength loss, not a crash.

**The UI never re-derives the rules.** `app/ui/game.js` validates every click
against `legalSequences()` from the position as it stood when the dice were rolled,
so the board can only reach positions OpenSpiel agrees are reachable.

## The Python originals are the source of truth

Move generation and the encoder are ports of C++ (OpenSpiel) and numpy. Neither is
trusted: `test/` compares them against gzipped fixtures generated in `../raccoon`,
including an end-to-end check that this engine picks moves worth the same equity as
the Python one on 1,000 recorded decisions. A divergence must block the deploy
rather than reach the board — do not weaken these tests to make a change pass.

`app/models/*.onnx` and `app/vendor/*` are large binaries that **are** committed;
the site cannot work without them. Regenerate the model and fixtures from
`../raccoon`:

```bash
cd ../raccoon
python scripts/export_web_model.py --checkpoint experiments/exp018-distill/checkpoints/ep22.pt
python scripts/export_web_fixtures.py
python scripts/eval_benchmark_pr.py --onnx ../raccoon-website/app/models/exp018-ep22-fp32.onnx
```

The last command re-scores the exported file; the site must quote *that* number,
because it describes the engine visitors actually play.

## Site conventions

- **Every path is relative.** The site must work both at the apex domain and under
  a GitHub project subpath. `loader.html` uses `src="app/main.js"`, and `main.js`
  resolves the model and worker against `import.meta.url`.
- **`CNAME` is build output**, listed under `resources:`. `quarto-actions/publish`
  force-pushes `_site` to `gh-pages`, so a CNAME written only by the Pages setting
  is wiped on the next deploy.
- **Numbers live in `_variables.yml`** and are rendered with `{{< var engine.pr >}}`
  etc. Change the measurement there, not in prose. The company name and CVR are
  required on the site by Danish law and are checked against a Google for Startups
  application — keep them exact.
- **Do not use `<aside>` in the app markup.** Quarto styles asides as margin notes
  and places them in grid lines that do not exist here, collapsing the board to a
  thumbnail.
- Claims about strength are hedged deliberately (cubeless, checker play only, no
  doubling cube). Keep that framing when editing copy, and add user-visible changes
  to `changelog.qmd`.
- Comments in this codebase explain *why* — the measured cost of a bug, the Python
  file a port must match, the constraint behind a workaround. Match that register
  rather than narrating what the code does.
